| テーブル | 役割 | 誰が書く |
|---|---|---|
| `leagues` | リーグ（シーズン）と換算ルール設定 | 運営がSQL直（wrangler） |
| `teams` | リーグ内のチーム（2つ） | 運営がSQL直（wrangler） |
| `members` | 人のマスタ（リーグ横断） | 運営がSQL直（wrangler） |

| `game_results` | 半荘ごとの4人の素点 | **アプリ（入力係）** |

## Postgres からの型の読み替え

SQLite の型は `INTEGER` / `REAL` / `TEXT` / `BLOB` の4つだけ。Supabase 版から次のように置き換える。

| Supabase (Postgres) | SQLite | 補足 |
|---|---|---|
| `uuid` | `INTEGER PRIMARY KEY` | rowid のエイリアスで最速。**手でSQLを打つ運用なので短いIDの方が実用的** |
| `timestamptz` | `TEXT`（ISO8601, UTC） | `DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))` |
| `date` | `TEXT`（`YYYY-MM-DD`） | SQLite の日付関数がそのまま使える形式 |
| `int` | `INTEGER` | 同じ |
| `text` | `TEXT` | 同じ |
| `boolean` | （使わない） | 論理削除は `deleted_at` の NULL 判定で表現 |

<Aside type="note" title="ID を uuid から INTEGER に変えた理由">
管理UIを作らず `wrangler d1 execute` でSQLを直接打ってデータを入れる方針（決定#11）だと、uuid は手打ちが現実的に無理。`INTEGER PRIMARY KEY` なら `seed.sql` が人間に読める形になり、URLも `/games/12` と短くなる。10人規模でID衝突の心配もない。
</Aside>

## スキーマ

```sql title="migrations/0001_init.sql"
CREATE TABLE leagues (
  id           INTEGER PRIMARY KEY,
  name         TEXT    NOT NULL,
  start_point  INTEGER NOT NULL DEFAULT 25000,
  return_point INTEGER NOT NULL DEFAULT 30000,
  uma_1st      INTEGER NOT NULL DEFAULT  30,
  uma_2nd      INTEGER NOT NULL DEFAULT  10,
  uma_3rd      INTEGER NOT NULL DEFAULT -10,
  uma_4th      INTEGER NOT NULL DEFAULT -30,
  created_at   TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  -- ゼロサムの成立条件（→ ポイント計算 / ゼロサムが成立する条件）
  CHECK (uma_1st + uma_2nd + uma_3rd + uma_4th = 0),
  CHECK (start_point  % 100 = 0),
  CHECK (return_point % 100 = 0),
  -- オカ = (返し点 − 持ち点) × 4 / 1000。負のオカは意味を成さない（オカなしは 返し = 持ち）
  CHECK (return_point >= start_point)
) STRICT;

CREATE TABLE members (
  id   INTEGER PRIMARY KEY,
  name TEXT NOT NULL
) STRICT;

CREATE TABLE teams (
  id        INTEGER PRIMARY KEY,
  league_id INTEGER NOT NULL REFERENCES leagues(id),
  name      TEXT    NOT NULL,
  UNIQUE (league_id, id)   -- 下の複合外部キーの参照先として必要
) STRICT;

CREATE TABLE league_members (
  league_id INTEGER NOT NULL REFERENCES leagues(id),
  member_id INTEGER NOT NULL REFERENCES members(id),
  team_id   INTEGER NOT NULL,
  PRIMARY KEY (league_id, member_id),
  -- team_id が「同じリーグの」チームであることまで強制する（→ 所属とチームの整合）
  FOREIGN KEY (league_id, team_id) REFERENCES teams(league_id, id)
) STRICT;

CREATE TABLE games (
  id         INTEGER PRIMARY KEY,
  league_id  INTEGER NOT NULL REFERENCES leagues(id),
  played_on  TEXT    NOT NULL,
  title      TEXT,
  created_at TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  deleted_at TEXT,
  -- YYYY-MM-DD の実在日付だけを許す（→ 日付の検証）
  CHECK (
    played_on GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
    AND CAST(substr(played_on, 6, 2) AS INTEGER) BETWEEN 1 AND 12
    AND CAST(substr(played_on, 9, 2) AS INTEGER) BETWEEN 1 AND
        CASE CAST(substr(played_on, 6, 2) AS INTEGER)
          WHEN 2 THEN CASE WHEN CAST(substr(played_on, 1, 4) AS INTEGER) % 4 = 0
                            AND (CAST(substr(played_on, 1, 4) AS INTEGER) % 100 <> 0
                                 OR CAST(substr(played_on, 1, 4) AS INTEGER) % 400 = 0)
                       THEN 29 ELSE 28 END
          WHEN 4 THEN 30 WHEN 6 THEN 30 WHEN 9 THEN 30 WHEN 11 THEN 30
          ELSE 31 END
  )
) STRICT;

CREATE TABLE game_results (
  id        INTEGER PRIMARY KEY,
  game_id   INTEGER NOT NULL REFERENCES games(id),
  member_id INTEGER NOT NULL REFERENCES members(id),
  -- 予約（まだ対局していない半荘）は NULL。→ 予約と確定
  -- CHECK は NULL のとき NULL を返す＝合格扱いなので、予約行はそのまま通る
  raw_score INTEGER CHECK (raw_score % 100 = 0),
  UNIQUE (game_id, member_id)
) STRICT;

CREATE INDEX idx_games_league_played  ON games(league_id, played_on);
CREATE INDEX idx_results_game         ON game_results(game_id);
CREATE INDEX idx_results_member       ON game_results(member_id);
```

<Aside type="tip" title="STRICT を付ける">
SQLite は既定だと `INTEGER` カラムに文字列を入れても通ってしまう。`STRICT` を付けると型が強制されるので、Postgres 相当の安心感が得られる。付けない理由がない。
</Aside>

## 制約・ルール

- `game_results` は 1 `game` につき必ず 4 行（**APIサーバー側で保証**。DBは `UNIQUE(game_id, member_id)`）
- `raw_score` は 100 の倍数、負数可（`CHECK (raw_score % 100 = 0)`）
- 素点合計 = `start_point × 4`、2-2 固定は **APIサーバー側でバリデーション**（DBトリガーにはしない。シンプル優先）
- 削除は `games.deleted_at` をセット。取得時は `deleted_at IS NULL` で絞る
- オカは `(return_point − start_point) × 4 / 1000` で導出できるので**カラムにしない**
- `games.played_on` の `CHECK` は **3つの条件をすべて満たす形でないと機能しない**（→ [日付の検証](#日付の検証)）
- **`game_results.member_id` が「そのリーグに所属しているか」は DB では検証できない**。外部キーは `members(id)` の存在しか見ないので、`league_members` に無いメンバーでも INSERT が通る（実測確認済み）。**APIサーバー側のバリデーションが唯一の防衛線**
- `leagues` の4つの `CHECK` は **pt計算のゼロサムを守る最後の砦**。`leagues` は管理UIを持たず運営が `wrangler d1 execute` で手打ちSQLを流すテーブル（決定#11）なので、アプリのバリデーション層を一切通らない。typo を止められる場所はここしかない
- 外部キーは D1 では**既定で常に強制**される。旧構成で必要だった `PRAGMA foreign_keys = ON` は不要（→ [技術スタック](/spec/tech-stack/)）

<Aside type="note" title="pt/順位はDBに持たない">
`game_results` に pt や rank のカラムは置かない。フロントで `leagues` の設定値から都度計算する。ルール変更時に過去分を再計算する手間がゼロになる。
</Aside>

## 所属とチームの整合

`league_members.team_id` を素朴に `REFERENCES teams(id)` と書くと、**別のリーグのチームを指せてしまう**。外部キーは `teams(id)` の存在しか見ないので、「リーグ1に所属しているのに、チームはリーグ2のもの」という行が通ってしまう（実測確認済み）。

これが起きると **2-2固定の判定が静かに狂う**。判定は `league_members.team_id` でグループ化するので、リーグをまたいだチームが混ざると「各チーム2人ずつ」の数え方そのものが崩れる。エラーは出ない。

複合外部キーで塞ぐ。

```sql
-- teams 側に参照先となる複合 UNIQUE を用意し、
UNIQUE (league_id, id)
-- league_members 側から (league_id, team_id) の組で参照する
FOREIGN KEY (league_id, team_id) REFERENCES teams(league_id, id)
```

これで「別リーグのチーム」「存在しないチーム」の両方が INSERT でも UPDATE でも弾かれる。`league_members` の `team_id` に単独の `REFERENCES teams(id)` は不要になる（複合FKが包含する）。

<Aside type="caution" title="入れるなら 0001 のうちに">
SQLite は `ALTER TABLE` で外部キーを追加できない。後から入れるには「新テーブル作成 → `INSERT INTO ... SELECT` → 旧テーブル DROP → RENAME」の再構築が要る。`0001_init.sql` が本番に適用される前が最後のタイミング。
</Aside>

## 予約と確定

「次に誰が対局するか」を先に登録できる（**予約**）。対局が終わったら素点を埋めて**確定**する。

予約も**4人が確定している必要がある**（2-2固定も守る）。決まっていないのは素点だけ。

| 状態 | `game_results.raw_score` |
|---|---|
| **予約** | 4行すべて `NULL` |
| **確定** | 4行すべて `NOT NULL` |
| **不正** | 一部だけ `NULL`（APIが弾く） |

`games` に状態カラムを持たせない。**「素点が入っているか」が状態そのもの**なので、二重に持つと食い違う余地ができる。

<Aside type="caution" title="予約は集計に入れない">
予約の半荘は **`scoreGame` に渡してはいけない**（素点が無いので pt を計算できない）。

- `computeStats` は**予約を集計から除外**する。半荘数にも数えない
- ただし**警告は出さない**。`broken`（4人ぶん揃っていない壊れたデータ）とは違い、**予約は正常な状態**
- 一覧では「予定」として**確定済みとは分けて**表示する
</Aside>

<Aside type="note" title="なぜ raw_score を NULL 許容にしたか">
`0` を「未入力」の印にはできない。**`0` は正当な素点**（箱下との区別もつかない）。

別テーブル（`game_reservations` 等）にする案もあるが、**2-2固定・メンバー重複・リーグ所属のチェックが二重になる**うえ、予約→確定のときに DELETE + INSERT が必要になる。同じテーブルで素点だけ後から埋める方が、**既存の `PATCH`（全置換）がそのまま使える**。

`NOT NULL` を外すのは `ALTER TABLE` ではできない（SQLite の制約）。**`0001_init.sql` が本番に適用される前が最後のタイミング**。
</Aside>

## 日付の検証

`played_on` は `TEXT` なので、素朴に `NOT NULL` を付けただけでは `'banana'` も `''` も `'2026-13-99'` も入る（実測確認済み）。日付でグルーピング表示する設計（決定#5）なので、ここが壊れると一覧が崩れる。

**形式（`GLOB`）+ 月の範囲 + その月の日数**を算術で検査する。`date()` 関数は使わない。

```sql
CHECK (
  played_on GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
  AND CAST(substr(played_on, 6, 2) AS INTEGER) BETWEEN 1 AND 12
  AND CAST(substr(played_on, 9, 2) AS INTEGER) BETWEEN 1 AND
      CASE CAST(substr(played_on, 6, 2) AS INTEGER)
        WHEN 2 THEN CASE WHEN CAST(substr(played_on, 1, 4) AS INTEGER) % 4 = 0
                          AND (CAST(substr(played_on, 1, 4) AS INTEGER) % 100 <> 0
                               OR CAST(substr(played_on, 1, 4) AS INTEGER) % 400 = 0)
                     THEN 29 ELSE 28 END
        WHEN 4 THEN 30 WHEN 6 THEN 30 WHEN 9 THEN 30 WHEN 11 THEN 30
        ELSE 31 END
)
```

<Aside type="danger" title="date() を使った実在日付チェックは SQLite のバージョンで挙動が変わる">
一見すると `CHECK (date(played_on) = played_on)` で実在日付を判定できそうに見えるが、**これはバージョン依存**で、実測すると次のように割れる。

| 入力 | SQLite 3.51 の `date()` | SQLite 3.32.3 の `date()` |
|---|---|---|
| `'2026-02-30'` | `'2026-03-02'` に**正規化** → 弾ける | **`'2026-02-30'` のまま** → **通ってしまう** |
| `'2025-02-29'` | `'2025-03-01'` → 弾ける | **そのまま** → **通ってしまう** |
| `'2026-04-31'` | `'2026-05-01'` → 弾ける | **そのまま** → **通ってしまう** |

D1 は `sqlite_version()` の呼び出しを許可していない（`not authorized to use function`）ため、**本番のバージョンを直接確認する手段が無い**。上の算術版なら `substr` / `CAST` / `CASE` という最も古い機能しか使わないので、**どのバージョンでも同じ結果になる**。

さらに `date()` にはもう一つ罠がある。`date('banana')` は **NULL** を返し、SQLite の `CHECK` は式が**偽のときだけ拒否して NULL は通す**ので、`date(x) = x` 単体では「日付として解釈できない値」が素通りする。算術版はこの問題も持たない。
</Aside>

<Aside type="note" title="この CHECK は validation.ts と同じ規則を書いている">
`src/lib/validation.ts` 側も `Date` を使わず正規表現 + 同じ閏年規則（4 / 100 / 400）で判定する。**両者が同じ規則を明示的に書いている**ので、一致は偶然ではない。

`Date` を使わない理由は JS 側にもある。`new Date('2026-02-30')` は 3/2 に繰り上がり、`new Date('2026-8-6')` はレガシーパーサが受理し、`new Date('2026/08/26')` はローカルタイム解釈になってタイムゾーン次第で前日にずれる。さらに `Date.UTC(0, 0, 1)` は **1900-01-01** を返す（0〜99 の年が 1900+n に写像される仕様）ため、`'0000-01-01'` は `Date` 系では原理的に扱えない。
</Aside>

**1,289 パターン**で検証済み（年18種 × 月10種 × 日7種 + 全角数字・アラビア数字・タブ・前後改行・前後スペース・`20260826`・`+2026-08-26` など異形式29種）。SQLite **3.51 と 3.32.3 の結果が完全一致**し、`validation.ts` の TS 実装とも**不一致 0 件**。`UPDATE` でも効く。

## 書き込みの原子性

半荘の登録は `games` 1行 + `game_results` 4行の**セットで初めて意味を持つ**。途中で落ちると3人分だけの壊れた半荘が残るので、必ず1トランザクションにまとめる。

D1 には対話的トランザクション（`BEGIN`〜`COMMIT`）が無く、原子化の手段は **`batch()`** だけ。渡した全文が1トランザクションとして実行され、1文でも失敗すれば**全体がロールバック**される。

```ts title="server/routes/games.ts"
const db = c.env.DB;
await db.batch([
  db.prepare('INSERT INTO games (league_id, played_on, title) VALUES (?1, ?2, ?3)')
    .bind(input.leagueId, input.playedOn, input.title ?? null),
  ...input.results.map((r) =>
    db.prepare(
      // batch 全体が1トランザクション＝他の書き込みは割り込めないので、
      // 直前に INSERT した半荘の id を MAX(id) で安全に参照できる
      'INSERT INTO game_results (game_id, member_id, raw_score) VALUES ((SELECT MAX(id) FROM games), ?1, ?2)'
    ).bind(r.memberId, r.rawScore)
  ),
]);
```

<Aside type="danger" title="last_insert_rowid() は使わない（外部キーでも防げない）">
`last_insert_rowid()` は「直前のINSERT」の rowid を返すので、2件目以降の `game_results` INSERT では **1件目の game_results の id** を返してしまう。`(SELECT MAX(id) FROM games)` なら全行から見て同じ値になる。

**厄介なのは、これを外部キー制約が捕まえてくれないこと。** ローカルの SQLite で実証した結果:

| 入った行 | 参照した `game_id` | 実際 |
|---|---|---|
| 1人目 | 22 | ✓ 正しい（今作った半荘） |
| 2人目 | **3** | ✗ **既存の別の半荘に混入** |
| 3人目 | **4** | ✗ **既存の別の半荘に混入** |

`games` に id 3 も 4 も存在するので `FOREIGN KEY constraint` は通ってしまい、**エラーは一切出ない**。結果として「新しい半荘には1人分しか入っていない」「無関係な過去の半荘に5人目が生えている」という壊れ方をする。半荘数が少ないうちは `game_results.id` が `games.id` の範囲に届かず**たまたま動いてしまう**ため、運用が進んでから静かに壊れ始める。

整合性はすべてAPI層の責任（バリデーションもRLSも無いのは旧構成と同じ）。`batch()` 全体が1トランザクションなので、`(SELECT MAX(id) FROM games)` は他の書き込みに割り込まれない。
</Aside>

## 削除済み半荘への書き込みを SQL で塞ぐ

`PATCH /api/games/:id` は「削除済みなら 404」だが、これを **SELECT で確認 → `batch()` で書く** の2段で実装すると、その隙間に論理削除が入り込む余地が残る（TOCTOU）。入力係が1人なので実運用でまず起きないが、塞ぐのは1行で済む。

`game_results` の INSERT で `game_id` を直値ではなく**サブクエリ**にする。

```sql
INSERT INTO game_results (game_id, member_id, raw_score)
VALUES ((SELECT id FROM games WHERE id = ?1 AND deleted_at IS NULL), ?2, ?3)
```

削除済みならサブクエリが NULL を返し、`game_id` の `NOT NULL` 違反で **`batch()` 全体が巻き戻る**。API はこの失敗を 404 に写像すればよい。

## アクセス制御（旧: RLS）

RLS は無くなったので、APIサーバーのミドルウェアで代替する。

| メソッド | 対象 | 制御 |
|---|---|---|
| `GET /api/leagues`<br/>`GET /api/leagues/:id` | 閲覧全般 | **誰でも可**（認証なし） |
| `POST /api/games`<br/>`PATCH /api/games/:id`<br/>`PATCH /api/games/:id/deleted` | 半荘の登録・修正（全置換）・論理削除 | **`X-Passcode` ヘッダが `WRITE_PASSCODE` と一致した時だけ通す**（→ [APIの形](/spec/features/#apiの形)） |
| `DELETE` | – | **エンドポイントを作らない**（論理削除のみ。事故防止） |
| 運営系テーブル | `leagues` `teams` `members` `league_members` | **書き込みAPIを作らない**。`wrangler d1 execute` でのSQL直操作のみ |

```ts title="server/auth.ts"
export const requirePasscode: MiddlewareHandler<{ Bindings: Bindings }> = async (c, next) => {
  // シークレット未設定は「認証なし」ではなく設定ミス。素通りさせない
  if (!c.env.WRITE_PASSCODE) {
    return c.json({ error: 'server misconfigured' }, 500);
  }
  const given = c.req.header('X-Passcode');
  if (typeof given !== 'string' || given.length === 0 || given !== c.env.WRITE_PASSCODE) {
    return c.json({ error: 'invalid passcode' }, 401);
  }
  await next();
};
```

<Aside type="danger" title="素朴な !== 比較は「ヘッダを付けない方が通る」状態を作る">
一つ前の版はこう書いていた。**これは書き込みAPIが無防備になる。**

```ts
// ❌ 使わない
if (c.req.header('X-Passcode') !== c.env.WRITE_PASSCODE) { ... }
```

`c.req.header()` はヘッダが無いと `undefined` を返し、`c.env.WRITE_PASSCODE` はシークレット未設定なら `undefined`。
**`undefined !== undefined` は `false`** なので、`if` に入らず **`next()` が呼ばれて素通りする**（実測確認済み）。空文字を設定した場合も `'' !== ''` で同じ。

| ヘッダ | シークレット | 結果 |
|---|---|---|
| 正しい値 | 設定あり | 通す（正常） |
| 誤った値 | 設定あり | 401（正常） |
| **無し** | 設定あり | 401（正常） |
| **無し** | **未設定** | **★素通り** |
| **空文字** | **空文字** | **★素通り** |

起きる条件は現実的だ。`.dev.vars` を置かずに `wrangler dev` したローカル、`wrangler secret put` を忘れた本番、シークレットを差し替える一瞬。**「認証が無い」のではなく「認証ヘッダを付けない方が通る」**という、テストでも気づきにくい形で壊れる。

シークレット未設定は **500（設定ミス）** として扱い、401（認証失敗）と区別する。
</Aside>

## マイグレーション

- `migrations/` に連番SQLを置き、`wrangler d1 migrations apply` が未適用分を順に流す（適用履歴は D1 が `d1_migrations` テーブルで管理）
- 旧構成の自前ランナー（`db/migrate.ts` + `PRAGMA user_version`）は**不要になった**
- 型は生成せず、`src/lib/types.ts` に**手書き**する（テーブル6個・カラム30個弱なので生成ツールに見合わない）。D1 が自動で作る `d1_migrations` はアプリから触らないので型を書かない
- 初期データ（メンバー10人・リーグ・チーム・所属）は **`db/seed.local.sql`**。`db/seed.sql` はプレースホルダ名のテンプレートで、**実名を書かずにコミットする**（→ [使い方](/spec/usage/#リーグ立ち上げ運営シーズン開始時に1回)）

```bash
wrangler d1 migrations create majan init     # migrations/0001_init.sql の雛形が作られる
wrangler d1 migrations apply majan --local   # ローカル（.wrangler/state/ 配下）に適用
wrangler d1 migrations apply majan --remote  # 本番に適用
```

<Aside type="caution" title="SQLite の ALTER TABLE は弱い">
SQLite は `ALTER TABLE ... ADD COLUMN` と `RENAME` しかできない。**カラムの型変更・制約追加・削除ができない**ので、後からスキーマを変えるときは「新テーブル作成 → `INSERT INTO ... SELECT` → 旧テーブル DROP → RENAME」の手順を踏む。Postgres より migration のコストが高いので、初回のスキーマは慎重に決める。
</Aside>

## バックアップ

一次防衛は D1 の **Time Travel**。毎分自動でスナップショットが取られ、無料枠でも**過去7日の任意の時点**に復元できる（決定#17）。

```bash
# 復元可能な範囲を確認
wrangler d1 time-travel info majan

# 指定時刻の状態に巻き戻す
wrangler d1 time-travel restore majan --timestamp=2026-08-25T13:00:00Z
```

7日より古い状態も残したい分は、定期的にSQLダンプを手元へ落とす。

```bash
wrangler d1 export majan --remote --output=./backups/majan-2026-08-26.sql
```

<Aside type="note" title="ダンプはただのSQLテキスト">
`export` の出力は `CREATE TABLE` + `INSERT` の羅列なので、ローカルの `sqlite3` に流せば**本番同等のDBファイルを手元で再現**できる。旧構成の「ファイル1個をコピーする」感覚は、この形で残る。WAL破損を気にした `sqlite3 .backup` の儀式は不要になった。
</Aside>
