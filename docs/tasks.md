### D-23: 個人成績の未定義値は `null` を返す（`NaN` / `Infinity` 禁止）★T5
リーグ開始直後は**全員が半荘数0**。素朴に割ると `0/0 = NaN`、`Math.max()` は `-Infinity`、`Math.min()` は `Infinity`（実測）。
`NaN` は画面に「NaN」と出るうえ、**比較・ソートで伝播してランキング全体を壊す**。
平均pt / 平均順位 / 各着率 / トップ率 / ラス率 / 最高・最低素点 は **半荘数0 なら `null`**。合計pt と各着回数は `0`。

### D-24: 平均順位は `scoreGame` の `rank` を使わず「占める順位」で計算する ★T5
`rank` はグループ先頭順位（`1,1,3,4`）。実測で Σ`rank` は同点の有無により **10 / 9 / 7 / 4** と変動するが、
**Σ占める順位は常に 10（=1+2+3+4）で安定**する。
`Scored[]` から導出できるので `scoring.ts` は変更不要:
```
占める順位 = rank + (同じ rank を持つ人数 − 1) / 2
```

### D-25: 着順回数は `rank` で数える。同点1位は全員が1着 ★T5
「トップ率 = トップを取った（分け合った）割合」と読むのが自然なため。
この結果、**全員の着順回数を横に足すと半荘数と合わない**（3半荘で `[5,3,1,3]` を実測）。
ただし**1人あたりでは 1着〜4着の合計が必ず半荘数と一致する**ので率は破綻しない。横に足した数字はどこにも表示しない。

### D-26: Recharts は使う。ただし**コード分割して登録フローに負担させない** ★T8
マネージャーが実測したバンドルコスト:

| 構成 | raw | gzip |
|---|---|---|
| React のみ | 190 kB | 60 kB |
| React + Recharts（2系列の折れ線） | 557 kB | 165 kB |
| **Recharts の追加分** | **+366 kB** | **+105 kB** |

現在のアプリは 336 kB / gzip 107 kB なので、素朴に入れると**約2倍（gzip 212 kB）**になる。
Recharts 3.10.1 は `@reduxjs/toolkit` / `react-redux` / `immer` / `reselect` / `victory-vendor`(d3) / `decimal.js-light` を引き連れてくる。

**判断**: 仕様（`tech-stack.mdx`）が Recharts を指定しており、手書きSVGに置き換えるとツールチップ・凡例・レスポンシブを自前で持つことになる。10人・たまに使う用途で gzip 212 kB は許容範囲（4G で1〜2秒、以降はキャッシュ）。**仕様を変えない。**

ただし **`React.lazy` でチャートを分割**する。理由は**入力係が半荘登録に使う経路（T7）にグラフのコストを払わせない**ため。入力は雀荘の電波が悪い場所で行われる可能性があり、登録が主目的の画面で 105 kB を待たせる理由がない。閲覧者が戦績を開いたときにだけ読み込む。

### D-27: 予約登録（山本さんの追加要件・2026-08-26）
> 試合登録は素点を入力せずとも**予約登録的な感じで登録できないか**。**次誰の試合があるのか**を分かるようにしておきたい。

山本さんへの確認で全て最小構成に決定:
- **予約でも4人必須**（2-2固定も強制）。「次に誰が対局するか」を示すのが目的なので、人が決まっていない予約に意味がない
- **予約を編集して素点を埋める**（専用の「結果入力」画面を作らない）→ **既存の `PATCH`（全置換）がそのまま使える**
- **一覧では予約を上にまとめる**

**スキーマ**: `raw_score INTEGER NOT NULL` → `raw_score INTEGER`（本番未適用なので `0001` を直接修正）
- 予約 = 4行すべて `NULL` / 確定 = 4行すべて `NOT NULL` / **一部だけ NULL は API が弾く**（`MIXED_SCORES`）
- **`games` に状態カラムを持たせない**。「素点が入っているか」が状態そのもの。二重に持つと食い違う
- **`0` を未入力の印にしない**。`0` は正当な素点で箱下と区別がつかない

**並び順**: 予定=日付昇順（近い順）／結果=降順（新しい順）。**目的が違うので向きが違ってよい**（前者は「次に誰が打つか」、後者は「直近の結果を確認・修正」）。

## レビューの原則

### 原則1: 「実行を要する緩和」は修正ではない
穴を見つけて緩和策を作った時点で満足しない。その緩和策が **「誰かが実行しないと効かない」種類か**を見る。

- 確認クエリ・チェックリスト・ドキュメントの注意書き → **緩和**（実行されなければ発動しない）
- DB制約・型・テスト・CI → **修正**（実行しなくても効く、あるいは自動で走る）

D-15（複合FK）で dev が確認クエリを緩和策として提示し、マネージャーが制約に格上げした経緯から。
`leagues` の `CHECK` 4本を入れた理由とまったく同じ論理。

### 原則2b: 深刻度は「仕様との距離」ではなく「利用者が止まるか」で付ける

reb が T7 で「メンバー選択にチーム別表示が無い」を **[Minor]** と判定したが、実際の利用者は
**「どのチームか分からないから登録ができない」** と報告した。**主機能が使えない = Blocker**。

reb の自己分析:
> 「仕様に書いてあるのに無い」で止まり、「これが**無いと登録という主機能が使えない**」まで降ろしていなかった。

**仕様との差分は深刻度ではない。** 「その差分によって利用者が何をできなくなるか」まで降ろして初めて深刻度が決まる。
`features.mdx` の1項目の欠落が Blocker にも Nit にもなりうる。

同じ回で reb が [Nit] とした「符号がメンバー変更後も残る」も、**間違った符号のまま保存できる**（＝誤ったデータが入る）ので Minor に格上げした。
**「頻度が低い」は深刻度を下げる理由になるが、「結果が誤ったデータ」なら Nit にはならない。**

### 原則2: 深刻度と「修正コストの時間依存」を分けて書く
「今なら安い / 後だと高い」は深刻度とは別軸。特に **SQLite のスキーマ制約は `0001` が本番適用される前が最後のチャンス**で、それを過ぎると再構築コースになる。
reb が D-15 を [Nit] としつつ「T11 の前が最後のチャンス」と添えたことが、格上げ判断の決め手になった。

### 原則6: 新しい概念を返り値に足したら、**表示する画面と、そこから遷移する先まで全部たどる**

dev が今日**3回**踏んだ型。

|---|---|
| `GET /api/leagues`（リーグ一覧） | **増えた後にどう切り替えるか**（ヘッダに `/` へのリンクが無かった） |
| `broken`（壊れた半荘を一覧で分岐） | **同じ `scoreGame` を通る `stats.ts`**（戦績画面は落ちたまま） |
| `unassigned`（名簿外メンバーの成績） | **ランキングから張ったリンクの先**（`/members/99` が「見つかりません」） |

いずれも「機能としては動く」が**目的の半分しか達成していない**。
マネージャー側も同じ見落としをしている（`GET /api/leagues` を足す判断をしたのは私）。

### 原則8: 「ユニットテストで見ている」と「その経路が通る」は別

`verify-api.sh` が109ケースあっても、**API 経由で一度も試していない機能**が8本あった（reb が画面の機能一覧と突き合わせて発見）。すべて**実際には正しく動く**ので、バグではなく**検査の抜け**。

| 抜けていた経路 | なぜ危ないか |
|---|---|
| **箱下（負の素点）の登録** | **仕様の中核**（トビ終了なし・箱下精算あり）なのに API 経由で一度も通していない |
| **別リーグへの登録** | D-13 の所属チェックを「**存在しないリーグ**」でしか試しておらず、`league_members` を `league_id` で絞っているかは**別リーグが実在して初めて検証できる** |
| **予約 → 確定 → 予約の遷移** | T13 の主機能が PATCH 経由で未検証 |
| 予約の POST 全般 | dev が発見（T13 の取りこぼし） |

**共通の原因**: ユニットテストが充実していると「検証済み」と感じてしまい、**経路の検証が抜けていても気づかない**。

**対策（reb 提案）**: `src/lib/api.ts` の export（`createGame` / `updateGame` / `deleteGame` / `fetchLeague` / `fetchLeagues`）× **画面から渡しうる入力の種類**（確定・予約・箱下・別リーグ・各バリデーション）の表を1回作り、`verify-api.sh` のラベルと突き合わせる。
**今回の抜けは全部この表の空欄だった。**

### 原則7: 症状ではなく原因を見る

**空白の多いグラフ**を dev は「見た目の問題（壊れて見える）」と捉え、軸を変える案（出場半荘だけを軸に）を検討した。
reb は「**推移は2点以上あって初めて意味を持つ**。長さ0の線は**図として何も伝えていない**」と捉え、`gameCount <= 1` なら図を出さない、という**軸をいじらない解**を出した。

> 私の見立ては症状を見ていて、原因を見ていませんでした。（dev）

症状に合わせて直すと**副作用のある解**（軸の圧縮＝存在しない連続性を描く）に行きがち。
**「これは何を伝えるための表示か」に戻ると、多くの場合もっと小さい解がある。**

### 原則5: 表示・検査・メッセージが「事実と違うことを言っていないか」

今日3回、**別々の場所で同じ形の問題**が出た。**通っている／表示されているが、内容が嘘**という型。

| 事例 | 何を言っていたか | 事実 |
|---|---|---|
| `verify-api.sh` の `grep 'VITE_'` | 「`VITE_` の使用を検出した」 | 検出したのは**「`VITE_` を使わない」と説明したコメント** |
| 登録画面の空欄 | 「素点の値が大きすぎます」 | **まだ何も入力していない** |
| 登録画面の合計欄 | 「合計 100,000 / 100,000」 | **読めない値を 0 として足していた**（赤いエラーと矛盾） |

いずれも「エラーが出ない」「条件を満たしている」という意味では正常に見える。**壊れているのは中身の真偽**。

**チェック方法**: 出力の1つ1つについて「**この文が事実として正しいか**」を、実装の意図とは独立に読む。特に
- 検査が**検査対象そのものではなく、その説明**を拾っていないか
- **「まだ無い」と「間違っている」**を混同していないか（未入力を誤りとして報告する / 未定義を 0 として集計する）
- エラーと同時に表示される**他の値が、そのエラーと矛盾していないか**

#### 系: 「応答があった」は「**目的のものが応答した**」ではない

`verify-api.sh` の「`WRITE_PASSCODE` 未設定なら 500」という **Blocker 検証が、静かに機能していなかった**（T10 で dev が発見）。

原因の連鎖:
1. `W() { npx --no-install wrangler "$@"; }` は**シェル関数**なので、`W dev ... &` の `$!` は**サブシェルの PID**
2. それを `kill` してもサブシェルが死ぬだけで、**孫の `workerd` がポートを掴んだまま残る**
3. 次に起動する「シークレット無し」のワーカーは**ポートを取れずに死ぬ**
4. **古い「シークレット有り」のワーカーが応答し続け**、401 が返る
5. **起動確認が `curl /api/health` が 200 を返すことだけ**だったので、**古いワーカーが答えても「起動成功」に見えた**

**検査は「起動した」と言っていたが、起動していたのは別のプロセスだった。**

**ルール**: プロセスやサービスの起動確認は、**「応答があること」ではなく「自分が起動したものが応答していること」**まで見る。
- ポートが**実際に空いたこと**を確認してから起動する
- 起動確認に**同一性の証拠**（PID・ビルドID・起動時刻など）を含める
- **確認手段が無い環境（`lsof` が無い等）では、静かに成功にせず落とす**

#### 系: 「自分のものだけを指しているつもり」のパターンを疑う

4例目が**表示ではなく操作**で出た。`pkill -f "wrangler dev"` が**他セッションの検証サーバーまで落としていた**（reb の検証が何度も SIGTERM で死んだ原因）。

| 意図 | 実際 |
|---|---|
| `VITE_` の使用を検出 | 「使わない」と説明したコメントを検出 |
| **自分が起動したサーバーを止める** | **他セッションのサーバーも止める** |

同じ構図。`--port` を書かなかったのは、`grep` にコメント除外を書かなかったのと同じ手抜き。

**ルール: プロセスやファイルを操作するときは「パターン一致」ではなく「自分が作った識別子」で指す。**
`$!` で PID を控えて `kill "$PID"`、`--port` を明示、`--persist-to` で専用ディレクトリ。
複数セッションが同じマシンで並行して動く前提では、**パターン一致は自分の範囲を超える**。

`validation.ts` の原因帰属（D-25 / 派生エラーの抑制）は、この原則を検証ロジックに適用したもの。

### 原則4: 検証コード自身が検証されているかを疑う
テストやスクリプトが「通っているのに何も見ていない」状態は繰り返し起きた。

| 事例 | 何が起きたか |
|---|---|
| T2 の 650,491 件 sweep | 合計保存という**弱い不変条件**しか見ておらず、ウマ逆順・rank誤り・全員pt=0 を1件も検出できなかった（reb が発見） |
| `verify-api.sh` の `sed` | 貪欲マッチが `duratio(n:0)` を拾い、**DB 件数が常に 0** として比較されていた（dev が発見） |
| `verify-api.sh` の `.dev.vars` | `--env-file` 省略で開発者の設定が自動で読まれ、「未設定 → 500」の検証が成立していなかった（dev が発見） |
| `verify-api.sh` の静的 grep | `grep -vc '//'` が「`//` を含む行」を丸ごと除外し、行末コメント付きの実コードを見逃す（reb が発見） |

対策は **mutation check**（わざと壊して検出されるか）と、**期待値を実装以外の独立な情報源から起こす**こと。

#### 例外: 等価変異（equivalent mutant）は「守られていない行」ではない

**どんな入力でも元と同じ挙動になる変異**は、原理的に検出できない。これは**テストの欠陥ではなく変異の性質**。

実例（T5・reb の判定）: `stats.ts` の `Math.round(pt * 10)` を外しても全テストが通る。
`scoreGame` の出力は `整数deci / 10` なので `(d/10)*10 === d` が常に成立し（**deci ±1,000,000 を総当たりして不一致0件**、round 無しで 50項×2万回累積してもずれ0）、`round` の有無で結果が変わらない。

**原則4の「守られない行」は「実行されない／値が検証されない行」を指す。** この行は全テストで実行され値も検証されている（結果が変わらないだけ）なので該当しない。

**では消してよいか → 消さない。** 消すと正しさが「JS の float で `(d/10)*10` が往復する」という**経験的性質**への依存になる。`Math.round` があれば float→整数deci の境界が**定義上**整数になり、その依存が消える。将来 pt が JSON 経由で来る・`scoring.ts` が表現を変える、といった変更で静かに壊れるのを防ぐ。

**運用**: 等価変異と判明した箇所は、コメントに「no-op だが境界を定義上正しくするため」と書き、mutation 表に**「等価変異（結果不変が仕様）」と注記**する。次に見た人が「検出できない＝弱い」と誤読しないようにするため。

### 原則3: 修正が「正常な操作まで塞いでいないか」も確認する
制約を足したときは、弾くべきものが弾かれることだけでなく、**通るべきものが通ること**も実測する。
dev が D-15 で「同リーグ内のチーム移動は通る」「3つ目のチームを足せる」を追加検証した例。

```sql
CHECK (
  played_on GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
  AND CAST(substr(played_on, 6, 2) AS INTEGER) BETWEEN 1 AND 12
  AND CAST(substr(played_on, 9, 2) AS INTEGER) BETWEEN 1 AND
      CASE CAST(substr(played_on, 6, 2) AS INTEGER)
        WHEN 2 THEN CASE WHEN CAST(substr(played_on, 1, 4) AS INTEGER) % 4 = 0
                          AND (CAST(substr(played_on, 1, 4) AS INTEGER) % 100 <> 0
                               OR CAST(substr(played_on, 1, 4) AS INTEGER) % 400 = 0)
                     THEN 29 ELSE 28 END
        WHEN 4 THEN 30 WHEN 6 THEN 30 WHEN 9 THEN 30 WHEN 11 THEN 30
        ELSE 31 END
)
```

**旧版（`date(played_on) = played_on` を使う3条件版）はマネージャーの指示ミス。** reb が3系統（CLI 3.51 / `wrangler d1 --local` / Python 3.32.3）で照合して発見。

| 入力 | 3.51 の `date()` | **3.32.3 の `date()`** |
|---|---|---|
| `'2026-02-30'` | `'2026-03-02'` に正規化 → 弾ける | **そのまま** → **通ってしまう** |
| `'2025-02-29'` | `'2025-03-01'` → 弾ける | **そのまま** → **通ってしまう** |
| `'2026-04-31'` | `'2026-05-01'` → 弾ける | **そのまま** → **通ってしまう** |

**D1 は `sqlite_version()` の呼び出しを許可しない**（`not authorized to use function` を reb が実測）ので、本番のバージョンを直接確認する手段が無い。

reb は「式が複雑になる割に得るものが小さい」として T11 での一度きりの確認手順を提案したが、**マネージャーがコストを実測して書き直しを選択**:
- 実測コストは **SQL 3行 → 12行**。使うのは `substr` / `CAST` / `BETWEEN` / `CASE` という最古の機能のみ
- reb 自身が「これは原則1でいう**緩和**」と認めていた。**原則1をそのまま適用**
- 副産物: `validation.ts` と**同じ閏年ルール（4/100/400）を SQL 側にも明示的に書く**ことになり、両者の一致が**偶然ではなく設計**になる

検証: **1,289パターン**（年18種 × 月10種 × 日7種 + 全角数字・アラビア数字・タブ・前後改行・`20260826`・`+2026-08-26` 等の異形式29種）で
`3.51 と TS の不一致 0 / 3.32.3 と TS の不一致 0 / 3.51 と 3.32.3 の差 0`。

### D-20: 素点・メンバーIDは `Number.isSafeInteger()` を要求する ★ゼロサムの4つ目の条件
`1e19 % 100 === 0` が成立するため、`% 100` による「100の倍数」判定は 2^53 を超えると**意味を失う**。
実測: `[1e19, -1e19, 50000, 50000]` は `validateGameInput` を素通りし、**`scoreGame` の pt 合計が `-3.2`**（ゼロサム破綻）。

- **API 側**: parse 段（D-18）で塞ぐ
- **`validation.ts` 側にも必要**: フロントは parse 段を通らず `validateGameInput` を直接呼ぶため。塞がないとフロントとAPIで判定が食い違う（dev の指摘）
- **上限は設けない**。安全整数の範囲内なら計算は正確でゼロサムも保たれる（`9e15` で確認）。合計 = `start_point × 4` の制約があるので単純な打ち間違いでは到達しない

### D-21: エラーレスポンスは2種類。**キー名で判別する**

| 業務ルール違反 | `{ "errors": [ ... ] }` |

### D-22: `requirePasscode` はメソッドを限定して掛ける

### D-18: 形の検査（parse）と業務ルールの検査は2段に分ける ★T4
`validateGameInput()` は**型どおりの `GameInput` を前提**にしている（`results` が配列でなければ `.length` で例外、`playedOn` が非文字列なら正規表現が `"undefined"` を評価）。
APIは JSON ボディという信用できない入力を受け取るので、**形の検査を先に置く**。

| 段 | 何を見るか | 失敗時 |
|---|---|---|
| 1. 形（parse） | `results` は配列か / 各項目の `memberId` `rawScore` が数値か / `playedOn` は文字列か / `memo` は文字列か null か | `400`（`{ error }`） |
| 2. 業務ルール | `validateGameInput()` | `400`（`ValidationError[]`） |

フロントはフォームの型が保証されているので1段目は不要。**APIだけが2段必要**。

### D-19: `memo` は500文字以内
理由はセキュリティではなく設計上のもの。**`GET /api/leagues/:id` が全半荘を1回で返す設計なので、1件の肥大が全員の取得を重くする**。
`ValidationErrorCode` に `MEMO_TOO_LONG` を追加。DB側には制約を置かない（可変長の妥当な上限は業務判断であり、後から変えたくなる可能性が高いため）。
`memo.length` は **UTF-16 コード単位**で数える（絵文字1つ = 2）。DB側に対応する CHECK が無いので不一致は起きず、T7 の文字数カウンタも同じ `.length` を使えば表示と判定が一致する（reb の申し送り）。

### D-14: `PATCH /api/games/:id` の `league_id` はリクエストから受け取らない ★T4 Blocker
dev が発見（マネージャーも reb も見落としていた）。ボディの `leagueId` を信じると**所属チェックが自己申告になって無意味化**する。
「リーグ2のメンバー4人 + `leagueId: 2`」を送れば整合してしまい、**リーグ1の半荘がリーグ2にすり替わる**。

| 送られてきたもの | 扱い |
|---|---|
| `leagueId` なし / DB と一致 | 正常（DB の値を使う） |
| **DB と不一致** | **`400`**。黙って無視は不可（「送ったのに効かない」が見えなくなる） |

- **`roster` を引く `league_id` も DB 由来の値**を使う（ボディの値で引いたら経路が変わっただけで同じ穴）
- `POST /api/games` は `leagueId` を受け取ってよいが、**存在しない `league_id` は `404`** で明示的に弾く（FK で落ちるに任せない）

### D-15: `league_members.team_id` は複合外部キーで「同じリーグのチーム」を強制する
dev と reb が独立に発見。単独の `REFERENCES teams(id)` だと**別リーグのチームを指せてしまい、2-2判定が静かに狂う**。
```sql
-- teams
UNIQUE (league_id, id)
-- league_members（単独の REFERENCES teams(id) は削除）
FOREIGN KEY (league_id, team_id) REFERENCES teams(league_id, id)
```
両者は「割に合わない/Nit」と判断したが、**`d1 info` で `num_tables: 0`（本番未適用）を確認済み**のため実作業は2行編集 + ローカル再適用のみ。マネージャー判断で格上げ。
列順が `(league_id, team_id) → (league_id, id)` で揃っていること（逆順だと型は通るが意味が壊れる）。

### D-8: T1 のスキーマ・seed はローカル SQLite 3.51 でドライラン検証済み
マネージャーが実機検証した結果（T1/T4 のレビュー基準として使う）:
- `leagues` の `CHECK` 4本（Σuma=0 / start%100 / return%100 / return≥start）は **INSERT でも UPDATE でも効く**
- `raw_score % 100 = 0` は**負の素点でも正しい**（SQLite の `%` はゼロ方向丸め。`-1500`→通す、`-150`/`-50`→弾く）
- 外部キー違反（存在しない league/member/game）は全パターン弾かれる
- **【訂正】STRICT の「型が強制される」の正確な意味**（dev の指摘で判明）。当初「TEXT混入を弾く」と記録したが一般化が広すぎた。実際に検証したのは `'abc'` で、それは弾かれる。正しくは:
  - `'25000'` `' 25000'` `'1e3'` → **通る**（それぞれ integer 25000 / 25000 / 1000 に無損失変換される）
  - `'abc'`（TEXTのまま）/ `'25000.5'`（REALになる）→ 弾く
  - **`CHECK` は変換後の値に効く**ので「TEXT で入れて制約をすり抜ける」抜け道は存在しない（`'25050'` は `start_point % 100 = 0` で弾かれる）
  - → 実害なし。`data-model.mdx` の STRICT の記述も修正不要
- `seed.sql` の**再実行は `UNIQUE constraint failed: leagues.id` で落ちる**＝二重投入で壊れない安全側
- `(SELECT MAX(id) FROM games)` パターンは4行すべて同じ `game_id` を指す（count=4 / sum=100000 で確認）
- **`last_insert_rowid()` は外部キーでも防げない**（下記）

### D-9: `last_insert_rowid()` の危険性を実証（T4 のレビュー基準）
FK を D1 相当（常時ON）にして実測したところ、`last_insert_rowid()` 使用時は
1人目 → `game_id=22`（正）/ 2人目 → `game_id=3` / 3人目 → `game_id=4` と**既存の別半荘に混入**し、
`games` に id 3・4 が存在するため **FOREIGN KEY 制約が通ってしまいエラーが出ない**。
半荘数が少ないうちは `game_results.id` が `games.id` の範囲に届かず**たまたま動く**ため、運用が進んでから静かに壊れ始める。
→ T4 で `last_insert_rowid()` が使われていたら **Blocker**。`data-model.mdx` に実証データつきで明記済み。
